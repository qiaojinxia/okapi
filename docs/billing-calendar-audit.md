# Token 与金额的日历归属核对

本阶段验证后端结算、统计投递和本地日期查询。固定源码 v6 的验收已完成；核心 API 核对目标仍在进行，不能据此宣称当前工作目录、所有统计指标或竞品能力全部验收。没有在本阶段修改前端、提交、推送或部署。

## 已复现与修复

### 非整小时偏移的午夜

旧本地日查询从 UTC 小时聚合恢复日期。Asia/Kolkata 的午夜前后各一秒落在同一个 UTC 小时；真实 ClickHouse 回归原本把两个事件合并到前一天，得到 `n=2, amount=200`，而不是两个日期各 `n=1, amount=100`。首轮实际退出 101，原失败记录保留。

新增独立、无 TTL 的 `mv_calendar_minute`，保留用户、密钥、分组、模型、客户端维度，以及请求事件数、Token 四轴与合计、四金额、错误、缓存写入与上报覆盖状态。不替换旧表，不自动回填或重复灌入历史。

查询按完整小时和对应维度比较分钟覆盖：完整时采用分钟事实；分钟不完整时采用整个旧小时，两个来源互斥。旧小时或分钟横跨本地日期、无法精确分配时返回 `statistics_calendar_history_incomplete`，不猜测 Token 或金额。UTC 继续使用原日聚合。契约见 [存储设计](database.md) 与 [DESIGN](../DESIGN.md)。

### 只剩旧 UTC 日聚合的历史

真实生产 SQL 转换探针构造了已保留的两条旧日事实：30 Token、200 micro。没有小时数据时，上海时区查询原本返回 `0/0/0`；因此不能把旧日事实缺乏细粒度来源解释为零用量。该探针验证生产查询转换与 ClickHouse，范围不是 HTTP 或完整投递链路。

现在八类日查询比较旧日聚合与保留小时的覆盖，缺口仅作用于受影响的维度与可能的两个本地日期。查询涉及缺口时返回上述明确错误；其他用户、其他维度和无关日期仍可返回正常的零。UTC 旧日事实仍可查询。新集成测试在清空原始明细后复验这些边界，避免把明细尚未过期时的正确结果当作保留期之后的证明。

### 结算恢复与定价夹具

PG 不可用时的结算恢复测试增加了精确钱包、账单与 outbox 断言：输入 20、缓存读取 2、输出 5、推理 1、缓存写入 3，最终费用 500 micro；恢复一次后余额 9,500，重复恢复不重复入账，outbox 仅一份且保留缓存写入。此项强化验证，没有在该固定版本中改变生产重试协议。

四组网关/跨界面夹具原本只创建定价草稿，未执行当前生产装载要求的显式发布，导致真实请求 `model_not_found`。夹具已发布测试价簿后再初始化网关；生产仍只读取已发布快照，未放宽业务断言。
