# 普通请求的持久结算

普通成功请求原来先关闭 Redis 预扣，再写 PostgreSQL 账单。Redis 故障、数据库写入失败或两步之间退出，都可能让实际费用失去恢复依据。现在成功结算先提交 PG，再同步 Redis。

## 提交与恢复

1. 用预扣时保存的用户、API key、资金池和最终计价结果构造账单；不根据结算时的新订阅状态重新选池。
2. 获取与长期冻结、订阅滚窗和余额修复共用的用户锁。账单、完整用量、价格快照、事件、用户/key 累计、统计 outbox 和 `billing_sync` 行在同一 PG 事务内提交。
3. 按持久记录关闭 Redis 预扣。提交后的 Redis 错误保留 `billing_sync`，不会将已完成的请求改判为免费或重新调用供应商。
4. worker 每轮先处理待同步记录，再处理过期预扣。重复执行不会增加第二笔账单、事件、key 用量或 outbox。同步完成才删除恢复行。

如果 Redis 已无预扣，不能区分“关闭成功但确认丢失”“已过期退款”和“Redis 数据丢失”。恢复不会猜测再扣一次，而是在同一用户锁下先完成该用户其他待同步关闭，再根据 PG 事件总额重建两池余额，同时保留其他活跃预扣与长期冻结。重建失败时继续保留恢复记录。

订阅滚窗与管理员对账修复先同步已提交的普通结算；同步失败时拒绝继续修改窗口或余额。管理员按日志退款也持有同一用户锁，先恢复待同步记录；恢复失败则拒绝继续，避免 PG 已退款、Redis 又按原消费扣费的竞争。到期清理沿用异步图片任务的行锁，普通结算与到期清理新增共用用户锁。

## API 行为

- Chat、Messages、Gemini、Responses、Embeddings/Rerank、同步图片、音频、视频、Realtime 断线结算和自定义透传都使用持久成功结算入口。异步图片和原生 Batch 保留各自已有的任务/结算事务。
- 普通 JSON 响应等待实际用量与冻结价格被 PG 或 Redis settlement journal 接受。现有 journal 在 PG 结算之前保存完整输入；PG 暂时拒绝但 journal 已接受时返回原成功响应并保留预扣，worker 恢复后按原输入只结算一次。journal 接受也失败时返回既有 `internal_error`，不能冒充已保存。Chat 的结算任务仍受下线等待计数跟踪，客户端断开不会直接取消该任务。
- HTTP SSE 的完成标记在 PG 或 journal 接受后发送。已输出的内容不能撤回，两种接受路径均失败时发送错误事件。活跃 Realtime/Responses WebSocket 的逐帧用量持久化尚未完成，不能把断线结算的恢复保证扩大到任意时刻强制终止进程。
- 账单中的 `balance_after` 暂为空，因为 PG 提交时 Redis 尚未关闭预扣。金额、Token、资金池和价格快照仍完整落盘，不填造一个“同步后的余额”。统计 outbox 与账单同事务；实时 KPI、成员/月度软计数与选路反馈仍是旁路计数，不保证进程在写入途中退出后自动补齐。

## 部署与边界

新增前滚迁移 `0016_billing_sync.sql`，无新依赖或公开路由。混合旧/新网关时旧请求仍可能走先 Redis 后 PG 的时序，应完成网关与 worker 的版本切换后再按新契约验收。本轮仅在隔离测试服务中应用迁移，未部署或重启开发实例。

持久提交需要数据库可用，普通响应收尾增加数据库事务等待；用户锁也会串行同一用户的结算与修复。尚未完成生产吞吐/延迟验收。数据库提交前强制退出、数据库长期不可用期间的完整用量保全、活跃 WS 中间用量恢复、统计旁路的自动补记以及历史数据保留与完整账本重建之间的兼容仍需后续验证，不宣称已经消除所有崩溃窗口。

资金锁修复已随后续完整工作区回归再次通过：950 项测试通过，包含领域/计价/账本 144 项，严格检查通过。执行结果、证明范围与失败复现见 [核心验证记录](core-api-verification.md)。

资金并发专项已复现原问题：持有恢复锁时，管理员充值与退款 HTTP 请求仍返回 200 并修改资金（两项回归测试均失败）。当前修复将管理员充值/退款、MCP 调整、兑换、支付入账与返利、注册赠送、单用户引导、迁移和余额到期清零纳入同一用户锁，具体回归结果见验证记录。

`operations::credit` 在锁内先准备 PG 事件/快照事务，再执行 Redis credit，最后提交事务。数据库明确拒绝或 Redis 明确拒绝时不提交单边资金变化；Redis 已执行但确认丢失、PG 提交失败、进程在两库之间退出仍可能需要对账。退款保持 PG 幂等状态先提交、Redis 按原池回补，锁覆盖两步。这里解决并发交错，没有将两库变为分布式原子事务。

支付订单变更为 paid、兑换码核销、注册赠送等业务状态与资金写入仍分步进行，崩溃后的业务重试补偿尚未完成；迁移的来源事件检查已移入锁内以防两个导入并发重复入账。到期清零在锁内重新检查有效期并锁住用户行，避免等待期间被延期的余额继续清零；重复 worker 不会再次扣款。低层 `pg::record_credit`/`pg::admin_refund` 仅处理 PG，运行入口应使用 `operations` 封装，不应绕过锁拼接双侧写入。


退款来源核对同时对齐了上述已有 journal 行为与旧测试断言；没有修改预扣或结算金额公式。Redis journal 的恢复保证依赖其实际存储可用性与持久配置，本阶段不证明 Redis 数据丢失或生产故障切换不会丢账。原 PG 拒绝测试失败及恢复只扣一次的验证结果随本阶段回执保存。
