# 长期额度冻结：账本契约与接入边界

`okapi_ledger::holds` 为供应商长任务提供独立的资金冻结。当前完成账本基础与 worker 对账接入，以及后续的 [批任务持久状态和结算门槛](native-image-batch-jobs.md)。后续已接入默认关闭的公开 Batch API、执行器、远端取消轮询及按成功图片结算；具体受控测试和未完成项见批任务契约，不能把账本测试等同于真实供应商联调。

## 身份与状态

迁移 `0008_balance_holds.sql`、`0009_balance_hold_cancellation.sql` 新增 `balance_holds` 及 `cancel_requested`。同一 UUID 固定用户、API key、模型、64 位十六进制请求摘要、最大金额和价格快照，重放时逐项核对。UUID 冲突或参数变化拒绝；取消和终态记录不删除。同一用户最多 128 条未关闭记录，余额不足的 pending 意图也占用名额，可用零费用取消释放。

| 状态 | 持久事实 | 恢复方式 |
| --- | --- | --- |
| pending | PG 已保存意图，Redis 可能尚未执行，也可能已冻结但 PG 确认失败 | 核对独立 Redis 凭证后继续确认；不能直接重新扣款 |
| held | 已确认资金来源和订阅窗口 | 核对 Redis 余额字段及独立凭证后才能向调用者确认准入 |
| closing | 账单、事件、用量、outbox 和结算凭证已在一个 PG 事务提交 | 按固定凭证释放资金，重复执行不再次退款 |
| closed | 已确认完成 | 同凭证重放只读；不同结算内容拒绝 |

每个用户持有独立 PG session advisory lock，跨越 PG 提交与 Redis 请求；与订阅注资、滚窗、结算和修复协作。取消任务或释放 guard 时关闭连接，防止带锁连接回到连接池。所有 PG 工作使用这一连接，单连接池也可执行。锁等待 5 秒、语句 10 秒、Redis 操作 10 秒；超时是待核查状态，不能推断请求未执行。这种连接使用方式尚无性能基准。

`reserve` 将类型化 PricingSnapshot 序列化后委托 `reserve_frozen`；后者仅用于从服务自身持久任务读取的原价格 JSON，不接受客户端报价。校验对象、group/epoch/mode 类型和 64 KiB 上限，再走相同身份/重放检查。实际 PG/Redis 用例验证重启后按保存的 epoch/价格冻结，而不采用已经变化的新报价。

## 冻结、结算与订阅窗口

- PG 先保存意图，再以同 `{uid}` 槽 Lua 修改 Redis，最后 PG 确认 held 并追加金额为零的 reserve 审计事件。冻结本身不是支出，不提前更新 API key 已用额度或统计消费。
- Redis `bal:{uid}` 中的 `h:<UUID>` 与独立 `hold:{uid}:<UUID>` 保存相同冻结凭证。金额是十进制整数字符串，最大值为 `9_007_199_254_740_991` micro-USD；入参、原余额、加减后的结果和恢复总额均检查。原余额必须在运算前校验，防止越界值舍入后进入允许范围。长期冻结不使用普通请求 `r:*` 的十分钟 deadline，但与普通请求共用 API key 并发上限，详见下节。
- 结算核对价格快照、group、epoch、身份和金额上限；媒体单位数只能减少。实际金额必须等于原额减优惠，discount 可为负以保留合法加价；失败/退款金额必须为零。四金额列、使用维度与原有 `record_settlement_in_tx` 共用入账路径；同一事务写账单、事件、钱包快照、key 用量、outbox 及 closing 状态，然后才退还未使用的冻结额。
- 选池继续采用既有规则：有效订阅余额大于零时使用订阅池，最后一笔允许越界；否则钱包必须足额。订阅窗口凭证为订阅 ID 加 `window_start` 的微秒值，续期保持不变。旧 Redis 数据缺少凭证时，只从截止时间完全匹配的有效 PG 订阅补齐，无法证明则拒绝。
- 同一有效订阅窗口退回未用金额；窗口过期、取消或已经换窗，未用额不补进新窗口，而在结算同一事务写负数 `sub_expire` 事件。旧任务的实际费用仍归原来的池。滚窗不会把长期冻结加进新配额；普通同步 `r:*` 的现有滚窗政策保持不变。
- 钱包退款仍回原钱包。余额到期清理的是当时可用余额；冻结资金不是可用余额。这里没有新增独立的“冻结钱包额度到期”政策。

## 与普通请求共用密钥并发上限

新冻结读取 PG 中当前 API key 的 `max_concurrency`，与资金准入使用同一用户锁和数据库连接。Redis 原子检查 `普通请求 conc:{uid}:k:<kid> + 长期冻结 hc:<kid> + 1 <= 上限`；普通请求也在预扣时检查相同总数。上限为空或不大于零仍表示不限。不同 key 的占用互不混用；一个已冻结批任务占一个名额，与其图片输出数无关，不代表供应商内部子请求并发受到此上限控制。

`hc:<kid>` 是 `bal:{uid}` 内不设 TTL 的派生字段，与 held 凭证同时增加，在真正关闭冻结时减少。重复准入、重复关闭、取消意图和尚未冻结的 pending 任务不增减它。提交回包丢失、执行器重启和等待远端取消期间继续占用；管理员降低上限不会撤销已持有名额，只阻止新准入。普通请求名额保留既有的同步回收机制，长期任务不会因普通计数器的 TTL 到期而释放。

旧数据缺少 `hc:` 时从当前 `h:*` 凭证推导，不先写入再验证；非法计数或无法解释的凭证拒绝准入。PG 权威修复根据最终 held 凭证清理、重建整个 `hc:` 索引，修复拒绝时不写入任何索引。Redis 整体丢失后，必须先完成 PG 权威恢复才能依赖这些占用；这里不保证恢复前的零费用普通请求仍能识别丢失的长期占用，也没有恢复普通请求丢失的在途状态。

旧凭证兼容不等于支持混用新旧准入实现：所有处理请求和冻结/关闭任务的实例须升级到此逻辑，切换前后已有占用可通过 PG 权威修复重建。旧实例既不会维护 `hc:`，也不会检查共享总数，混合运行期间不能保证此并发上限。

账本返回 `Admission::ConcurrencyLimited` 时保留 pending 意图而不冻结资金。批任务执行器约三秒后重试，公开状态保持 funding，不将排队伪装为上游错误；用户可按既有取消流程结束等待。任务创建时的容量、次数准入及幂等保留规则仍适用。

## 未确认冻结的取消

pending 只能以 Failed/Refunded、金额为零结算，不能直接记为成功消费。先在 PG 保存 `cancel_requested`，再执行 Redis seal：已发生冻结时使用原凭证退款；尚未冻结时写入永久的零退款关闭凭证，挡住迟到的 reserve 命令。禁止删除 pending 行后重建。

若 seal 已完成而账单事务失败，取消标记仍保留，后续准入被拒绝；调用者重试零费用结算完成收尾。Redis 丢失后，repair 根据 PG 取消标记重建拦截凭证。该行为只处理尚未向调用方确认的准入；已提交供应商的任务必须先查明远端终态，不能因为用户点取消或远端仅确认收到 cancel 就退款。

## 对账与恢复

两池分别满足：`可用余额 + 普通预扣 r:* + 活跃长期冻结 h:* = billing_events 对应 pool 的累计金额`。

worker 对账纳入 h:*，十分钟过期清扫仍只处理 r:*。修复时先获取用户锁，再读取 PG 事件总额与持久冻结清单；单个 Lua 脚本在全部校验通过后，一次性重建两个池、缺失的 held 凭证及 closing 的关闭凭证，保留普通预扣。未知 active hold、格式错误和资金来源矛盾时拒绝修复，不覆盖证据。

PG held 但 Redis 缺失时，普通重放返回恢复错误；只能由按 PG 账目重建的修复恢复，不能把它当作新任务再冻结。closed 独立凭证没有 TTL，也未实现 GC，防止延迟命令在凭证过期后再次扣款；长期存储清理须与批任务/账单生命周期一并设计。

订阅授予/滚窗本身仍沿用原有 PG 状态、Redis 注资、PG 事件的多步流程；本次用户锁解决其与冻结结算之间的交错，不将该流程宣称为跨存储原子事务。注资途中故障、真实基础设施中断和供应商计费仍需后续业务级恢复验证。
