# 渠道成本来源与回放

渠道相对成本是站内配置估算，不是厂商发票。普通成功计费的公式保持
`list_price_micro × relative_cost_milli / 1000`，使用 checked i128 和 i64 范围检查。
缺工具价/量、负参数或溢出不能产生完整已知成本。

此前结算重新查询渠道成本，实际等待中的 Anthropic JSON 请求在系数从 1250
改成 2500 后，成本从应有的 27000 变成 54000；消费/原金额/优惠仍为
21600/21600/0。实际失败测试及固定源码见
`target/test-evidence/cost-source-failures-20261001/failures.json`。

## 新账单

所有使用候选渠道的成功路径在本次最终报价快照中保存
`upstream_cost_basis`：`version=1`、`source=selected_channel`、`channel_id`、
`relative_cost_milli`、`list_price_micro`。渠道/密钥故障转移采用最终成功的候选；
长连接、同步媒体、异步图片任务均沿用上游请求前选中的候选配置，不结算时重查。
候选缓存的既有新鲜度不变；此契约保证候选一旦选定，后续改价不影响该请求。

系数缺省 1000；有效配置为零时成本明确零。调度权重另对除数取至少 1，
不能将这个调度下限写进账单。JSON 依据随 PG、outbox、CH、归档回执与
Redis 恢复日志传递；无需新列或迁移。依据与账单渠道/标价不匹配，或未知版本、
非法系数时保持未知并告警，不读取当前配置补成已知。

异步图片任务仍经任务完成事务写入，完成前调用统一结算准备以计算冻结成本。
原生图片批处理采用先按系数、后按 500 千分比取整的既有成本公式；
依据另保存 `batch_cost_ratio_milli=500`，持久化 unit_quote 的成本是结算来源，
恢复与部分退款不重新应用两次系数。失败/退款原有语义保持。

## 旧载荷

已有金额与历史快照不重写。尚未生成成本且没有依据的旧成功载荷保留旧查价
兼容路径，并标明 `source=settlement_lookup_legacy`，不得宣称候选时冻结。
已有成本的恢复输入直接沿用原金额，已存在但无效的依据不得走兼容查价。
工具成本未知的载荷仍保持 PG NULL、事件/CH 数值 0 与 known=false。

## 已结算账单的管理员退款

退款只冲销原账单四金额，不重新报价或读取当前渠道配置。事件的
`upstream_cost_known` 由原账单成本是否为 NULL 决定，明确零成本保持 true，
未知成本使用数值 0 与 false。负额冲销保留原 `pricing_snapshot` 为
`ratio_snapshot`，其中成本依据和正数工具报价是原账单来源，不是新增使用量。
原账单与归档回执均只翻转账务状态；退款调整的 Token 计数保持零，工具实测
用量不复制，调用和测量样本不增加。

现存归档回执没有独立 `pricing_epoch` 列。活动账单沿用原列；归档退款只能
使用原快照中明确记录的整数 epoch，缺失时保持 NULL，不用当前版本补齐。
旧空快照沿用空字符串，不伪造成本依据。四金额取反须 checked，无法表示的
冲销拒绝并回滚完整退款事务。无需修改表、Redis 或 Lua 契约。

本阶段验证范围为已知正成本、明确零成本、未知成本的活动/归档退款，以及
重复退款和溢出拒绝。结果以实际固定源码测试回执为准，不代表核心功能已全量
验收，也不证明历史已投递的缺字段退款事件已修复。
