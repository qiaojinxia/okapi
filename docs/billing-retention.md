# 历史账本结转与明细保留

配置 `retention_months` 后，详细日志可以过期，但余额、退款金额和请求防重身份必须继续有效。迁移 `0019_billing_retention.sql` 为后续分区清理增加财务结转；不会凭空恢复升级前已经删除的历史。已有历史缺失需要从备份恢复或经过核对后补账。

## 持久数据

- `billing_event_carry` 按用户、支付池、actor、事件类型保留净变动与事件数。净额为零也保留行，迁移导入标记不会随日志清理消失。
- `billing_balance_totals` 汇总当前事件和结转，用于两个池的对账、重建及结算缺凭据恢复。`billing_actor_totals` 用于导入防重和累计邀请奖励。
- 结转金额使用无小数的 `NUMERIC(38,0)`，避免相抵的生命周期累计额提前超过 bigint；最终余额必须能转换为 bigint 并通过 Redis 既有安全整数校验。没有浮点计算。
- `billing_record_receipts` 保存请求 ID、归属、原支付池、账单状态、四金额、定价快照与用量说明。省去过期请求的 IP、UA、性能等日志字段。
- `billing_financial_records` 合并实时账单和历史财务凭证，结算防重、退款定位、过期预扣和图片恢复使用同一财务来源。历史凭证保留原 request_id 唯一约束。

历史退款仍走原有资金事务：状态从 committed 改为 refunded、写退款事件、回补原支付池、回冲 key 用量、写四金额负数 outbox、建立持久入账意图。重复退款返回 already_refunded；已退款请求不能再次结算。

## 清理与并发

发现候选分区时先持有共享历史锁，读取完目录后提交，再逐分区申请排他锁。这样不会与另一个清理任务的 DROP 交错而使 `pg_get_expr` 读到已经消失的 OID。外部 DDL 仍可能使分区定义为空；空定义不能通过边界校验，不能据此结转或删除。

每个分区独立事务：取得结转排他锁，核实真实父表、schema、OID、命名和 UTC 月边界，锁定分区，再次验证，结转财务数据后 DROP 并提交。任一步失败都回滚该分区的结转与删除；此前已完成的分区不回滚。禁止 CASCADE，外部依赖会阻止删除。凭证 request_id 冲突也会阻止清理，不能静默忽略账单。

读取合并财务历史的事务先取得同一共享锁，再执行 SQL，避免在迁移和删除之间读到缺失或重复的金额。清理任务之间串行；用户资金操作保留原来的用户锁与请求锁。共享锁事务应尽快提交，不跨后续 Redis 重建流程长期持有。

保留当前月及之前 N−1 个自然月。`0`、负数或无法表示的超大保留期不清理。DEFAULT 分区、不属于目标父表的同名表、名称与实际分区边界不一致的表不删除。每个分区设 5 秒锁等待和 10 秒语句上限；大分区可能需另行维护，尚未完成大规模在线清理性能验收。

## 范围

这是资金正确性保证，不表示所有历史日志仍可查询。明细接口仍遵循日志保留期，按日期的统计不会拿结转净额伪造旧事件日期，ClickHouse TTL 独立。财务凭证和 actor 汇总自身尚无到期删除策略。

仅在隔离数据库与 Redis 验证；未应用至开发/生产环境。此改动不解决订阅发放的 source 幂等、权益快照和跨存储中断恢复，后续继续验证。

## 本轮验证

五项业务故障先实际复现，再修复。隔离环境完整后端回归 978 项通过、0 失败/忽略/软跳过，其中历史留存 14 项；严格 Clippy、SQLx 离线编译和静态守卫通过。覆盖钱包/订阅原池退款、四金额冲销、退款/结算重放、两池修复及在途保留、冷余额与缺凭据恢复、零净额导入标记、邀请奖励累计、真实分区边界、并发清理、读锁互斥、DROP 失败回滚、凭证冲突拒绝和大额相抵累计。完整执行与局限见 [核心验证记录](core-api-verification.md)。

上述是历史阶段结果。后续支付全量回归再次执行并发清理时发现目录读取空值（`worker_retention::concurrent_pruners_carry_each_partition_once`），该轮完整执行退出 101。当前已增加候选发现共享锁与可空定义校验，修复复测结果继续记入核心验证记录，不能用此前通过记录覆盖后续失败。

修复后历史留存 14 项定向全部通过，并在支付阶段第二轮完整回归（1,031 passed、0 failed/ignored/软跳过）中再次通过；在线及离线严格 Clippy 通过。复测保留并发仅结转一次、读锁互斥、真实边界、依赖阻止 DROP 和余额恢复断言，未放宽删除条件。详见核心验证记录的第二轮日志与源指纹。
