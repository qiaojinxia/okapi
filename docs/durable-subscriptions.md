# 订阅权益与持久发放

订阅购买、兑换和管理员发放先在 PostgreSQL 受理。受理成功不等于 Redis 余额已经可用；暂时无法兑现的操作保留身份和原始权益，由 worker 重试。

## 权益快照

`0020_subscription_snapshots.sql` 为订单与兑换码增加 `subscription_snapshot`，为订阅实例增加套餐名、展示名、周期和分组快照。报价下单、创建兑换码时固定权益；发放时使用该快照。禁用套餐或修改配额、周期、分组不会追溯改变已购买、已发码或正在使用的权益。

同套餐 ID 仅在配额、周期、分组也相同时才能续期。续期只延长有效期，不重置额度。付款前检查冲突；付款期间条件发生变化时，回调保留已付权益并报告 `subscription_active`，旧订阅结束后再发放。升降级折算尚未实现。

取消只撤销这次订阅实际新增的原始分组。原已具有的成员资格不删除，改套餐配置后也不会误删其他分组。

## 受理与兑现

`0021_subscription_grants.sql` 新增两张表：

- `subscription_grants`：永久操作 UUID、递增顺序、用户、来源、权益快照、操作者、兑现后的订阅 ID/结果、时间与固定错误代码。`UNIQUE(user_id, source)` 防止同一订单、兑换或管理员幂等键重复续期，结束后的旧来源也不能重新激活。
- `subscription_sync`：用户级待同步标记，与订阅状态及财务事件一起提交。它不保存会过时的 Redis 目标值，恢复时读取当前完整财务历史。

支付订单翻转为 paid、兑换码标记已使用，分别与发放意图在同一事务提交。写入意图失败则来源状态也回滚。受理后即使 Redis 故障，合法支付回调仍可确认，worker 不依赖支付平台再次回调来兑现。

兑现持有账本用户锁，按该用户受理顺序处理，每次最多 32 条。创建/续期订阅、分组变更、`sub_grant` 事件或待同步标记、发放回执在同一 PG 事务提交。某用户恢复失败会记录错误，继续处理本批其他用户；数据库查询整体失败仍向调用方返回错误。

滚窗和结束订阅也先提交 PG 状态、`sub_reset` / `sub_expire` 事件与待同步标记，再同步 Redis。PG 失败不提前发额度或收分组；Redis 失败保留恢复任务。滚窗在用户锁内重读当前窗口，旧扫描结果不能再次重置已消费的新窗口。

## 余额恢复

PG 第二池目标为新配额加上仍然冻结的金额，事件记录目标与当前完整历史总额的差值。普通预扣和长期冻结均纳入计算；Redis hash 丢失时，已确认的长期冻结仍从 PG 计算。恢复从两池权威总额扣除仍活跃的冻结，重建可用余额、窗口、持久凭据与资金操作序号。

`hold_repair` 增加余额 hash 指纹前置条件。调用方读取清单前取得指纹，Lua 写入前再次比较；期间发生扣费、入账或预扣变化则返回 `recovery_required`，不写余额。这样，迟到的旧修复不能覆盖新扣费。所有 keys 保持同一 `{uid}` 槽；金额仍使用精确整数。

长期冻结跨窗口的未使用部分按原有 `sub_expire` 契约处理。普通同步预扣没有窗口身份，其跨窗口退回规则不能据此宣称已与长期冻结完全等价。

## HTTP 契约

- 管理员发放支持可选 `Idempotency-Key`（1–128 个可见 ASCII 字符）。范围为管理员和目标用户；同键同套餐返回原操作，同键不同套餐返回 409。省略键表示一次新的发放/续期意图。
- 发放响应包含 `operation_id`、`pending`、`outcome`、`subscription`。已受理未兑现时订阅为 null；PG 已兑现但余额未同步时可用余额与截止时间为 null，不能展示成已可消费。结束后的历史回执可用额度为 0，不读取当前其他订阅的余额。
- `GET /api/me/subscription` 与 `GET /admin/users/{id}/subscription` 增加 `pending_grants`、`pending_next_before`。待发放记录固定每页 20 条，按受理序号倒序，使用 `pending_before` 取后续页；非正数/非整数游标返回 400。门户仅返回当前用户记录。
- 待发放项包含操作 ID、套餐名、受理时间与 `subscription_active` / `delivery_pending` 等固定原因码。历史订阅仍保留最近 20 条的既有契约。

## 并发维护与有界重试

`0022_subscription_retry.sql` 增加实例 `maintenance_retry_after`、发放队列与待同步队列的 `retry_after`。到期扫描只提供候选，worker 在用户锁内重新读取状态、有效期和窗口后才决定结束或滚窗。先完成的续期不会被旧扫描取消；两个 worker 的并发滚窗只产生一次事件并只计一次成功维护。

单用户维护失败会记录 `failed` 数量及错误，并延后 60 秒再选取该实例；同批其他用户继续处理。延期写入核对扫描时的有效期和窗口，避免把新续期或新窗口一并延后。待发放及 Redis 待同步恢复也按用户退避，因此即使 batch limit=1，坏用户也不会永远占据队首。用户的直接重试不受 worker 退避限制；结束旧订阅会立即解除该用户待发放权益的退避，续期/滚窗会清除实例维护退避。

该保证不替代 PostgreSQL 的可用性：扫描或退避记录整体写入失败仍有日志/错误证据。60 秒来自本地后台恢复节奏，不是对外到账时效保证。

## 可售校验与支付报价

管理端拒绝超过账本安全整数范围的配额和价格，以及不能表示为有效到期时间的订阅天数。门户下单再次验证实际条款；旧数据即使绕过管理端校验，也不会直接生成不可兑现的订单。续购按当前有效期与现在的较晚时间计算，日期溢出在下单前拒绝。已受理来源的幂等回执仍保留。

支付换算使用整数公式 `ceil(micro_USD × rate_milli / 10,000,000)` 得到原币分数，以 i128 保存中间值，避免 i64 饱和乘法少收金额，也避免先截断到微单位后出现零元报价。USD 使用 rate_milli=1000。汇率必须为正；原币分数必须落在 `recharge_orders.pay_amount NUMERIC(12,2)` 的范围内，越界在写订单前返回 400，不修改表的金额精度来迁就异常输入。此处只修正报价，实际支付平台额度约束与回调金额/支付状态核对须单独验证。

## 升级与验证边界

迁移为旧数据使用升级时可取得的套餐配置补快照，无法还原此前已被修改的条款。历史实例缺失有效周期等坏数据会使迁移失败，不能默认猜测条款。迁移不会盲目重放旧 paid 订单或已用兑换码；新持久发放保证从新流程受理成功起生效，旧孤立权益需要独立审计。

验证入口是 `console_subscriptions::recovery`、`durable_holds` 与 `pg_settlement` 中的持久恢复测试；实际运行结果记录在 [核心验证记录](core-api-verification.md)。测试使用本地真实 PG/Redis 和受控支付上游，不代表实际支付平台、生产负载或全竞品功能验收。此次未修改前端、未部署。
