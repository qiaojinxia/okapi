# 钱包入账与退款的持久恢复

`0017_fund_transfers.sql` 与 `0018_fund_transfer_sequence.sql` 引入 PostgreSQL 入账意图及操作序号。订单支付、钱包兑换、管理员调账与退款先持久化，再写 Redis；Redis 故障不再抹掉已经提交的资金操作。

## 事务与确认

钱包支付回调在同一用户锁、同一 PG 事务内提交：订单 `paid`、`billing_events`、`users.balance_micro`、`fund_transfers`。钱包兑换同样提交核销、资金记录，以及套餐附带的分组/有效期。事务失败时这些变更一起回滚。已核销兑换码继续返回 404，重复支付回调继续成功应答，不产生第二笔入账。

管理员退款将账单退款状态、退款事件、金额/用量回冲和待入账记录一起提交；Redis 待回补不再丢失。普通管理员/MCP 入账、在线迁移余额也使用待入账记录。PG-only 离线导入保留原语义，不自动向已有热余额追加。

Redis `fund_transfer.lua` 在同一个 `bal:{uid}` hash 原子写余额及 `c:<operation_uuid>` 凭据。凭据是 `avail|<delta>` 或 `sub|<delta>`；重复参数只确认已执行，冲突、非法整数、溢出全部在写入前拒绝。整数必须是规范十进制，范围为 ±(2^53−1)。

完成顺序：Redis 原子执行 → PG `applied_at` → Redis 删除凭据 → PG `cleaned_at`。任意相邻步骤之间退出都可重试。用户 hash 永久保留 `fund_seq` 操作序号，和余额在同一次 HSET 写入。序号按完整 PG bigint 的十进制字符串比较，不转成 Lua 浮点。PG 用户锁保证接受和应用顺序；旧序号的迟到 EVAL 不再加钱，即使 c:* 凭据已清理。已确认应用的操作仅重试清理。历史 PG 操作记录保留供核对；尚未增加自动历史清理。

`UserGuard::synchronize` 先关闭普通已提交结算，再关闭长期冻结，再恢复资金操作。余额重建先校验未完成凭据，再将全部已接受操作的最高序号（含已清理操作）和余额一次 HSET 写入，避免修复已包含一笔充值后又重新加钱。序号不得单独清除或过期。余额 hash 丢失时，钱包使用 PG `users.balance_micro` 快照重建并扣除仍存活的冻结；订阅池沿用现有事件汇总。worker 扫描未完成记录，使用新连接也能恢复，不依赖原 HTTP 任务或第二次支付通知。

## HTTP 结果

正常情况下原 `balance_after_micro` 仍是实际热余额。数据库已受理、热余额尚不能确认时，该字段为 `null`，同时返回 `pending: true` 和 `operation_id`。这表示资金操作已接受，调用方应等待恢复，不应当作失败再提交一笔独立充值。成功落账时 `pending: false`。支付网关回调在数据库持久接受后按其协议返回成功。

## 验证范围与剩余问题

验证真实 Redis/PG 故障窗口：HTTP 支付、兑换、退款；Redis 已执行但 PG 未确认；PG 已确认但凭据清理未确认；清理后的迟到写入及完整 bigint 序号；重建与待入账相遇；余额键丢失；单连接池；非法凭据/大整数；订阅来源池退款。

本阶段覆盖钱包兑换/支付入账及退款，不等于所有购买权益都已有恢复队列。订阅套餐购买/兑换的激活、返利与注册赠送在业务入口和入账之间的中断、余额到期清零仍需独立补偿验收。管理员独立调账的网络重试尚未增加客户端幂等键；操作 ID 不等于相同 POST 自动去重。历史上已丢失且没有待入账记录的订单，不会被新 worker 自动推断并补发，需要按账本核对。恢复积压的公平调度仍需补齐。通用对账和普通结算丢凭据后的重建依赖全历史事件；非零 retention_months 会清理这些分区，可靠的历史结转基线尚未统一。本阶段的冷钱包快照测试不能证明通用对账在清理历史后也正确。没有修改前端，没有部署。
