## 问题与口径

旧 raw 采集把未提供的耗时写为 0，旧聚合均值用全部请求作分母；TPS 则把没有对应耗时的输出 Token 也放入分子。这会把均值算低、速度算高。模型耗时分位数同样将缺失值当作零。PG 账单均值还排除了失败请求，并使用四舍五入，与看板的整数除法不同。

新增 `latency_reported`，用显式标记区分明确测得 0ms 和未采集。负数、小数、字符串及超过 UInt32 的元数据计为未知，不伪装成有效零；首字元数据同步使用相同的数值校验，避免超大正数获得错误的“已采集”标记。

- 平均总耗时：已采集请求的毫秒总和 / 已采集请求数，向下取整为整数毫秒。包含成功、失败及非流式调用；PG 待结算账单不参与。
- 输出速度：**同一批已采集请求**的输出 Token 总和 / 耗时毫秒总和 × 1,000,000。API 的 `tokens_per_1k_sec` 与 `avg_output_tps_milli` 除以 1,000 即 Token/s。这包含等待时间，Realtime 还包含会话停顿，不是纯解码速度。
- 明确 0ms 参与均值与分位数；所有样本总耗时为 0 时速度为 null，不能伪造 0 Token/s 或无穷大。没有有效样本时均值、速度及分位数为 null。
- 账单/总量中的输出 Token 仍包含全部请求；`performance_completion_tokens` 是用于计算速度的配对输出，二者不一定相等。

## 历史与覆盖

独立的小时完整维度、模型小时、渠道五分钟 MV 保存请求覆盖数、有效样本数、条件耗时和/输出和；模型、渠道额外保存有效分位数。旧请求、费用及 Token 聚合保留，不删除或 POPULATE 回填。TTFT 与总耗时共用覆盖恢复算法，各自使用独立的采集条件。

新聚合覆盖不足时，仅在限定时间、用户及缺口粒度内读取 raw。新聚合与 raw 重叠，必须择一，不能相加；不能恢复完整范围时均值、速度和分位数返回 null。旧 raw 的正耗时可确认已采集，旧零值无法区分未知与真实零。聚合暂时领先于请求总量也不能被标为完整。

`latency_observed_requests`、`latency_history_complete` 和 `latency_history_coverage_bp` 表示历史数据覆盖。`latency_samples`、`latency_sample_coverage_bp` 表示其中有多少请求实际提供耗时。个人用量原有 `performance_requests` 保留为历史请求覆盖数，不能把它当作有效样本分母。
