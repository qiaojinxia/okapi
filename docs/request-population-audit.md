# 退款与调用统计的样本范围

状态：已实现独立分类聚合与读取来源，底层 ClickHouse 两个集成场景已通过；真实 HTTP 组合查询仍在修复与验收中，尚不能宣称端点全绿。原始财务事件没有重复投递，Token 与净费用正确；不能用已有回归全绿宣称请求数和测量覆盖率也正确。

## 实际复现

以固定 v12 后端作为生产源码，复用正式网关、账本、管理员退款与 outbox 投递。测试新增的只有独立探针夹具，未改生产实现。专用 ClickHouse 数据库接收该用户的两条财务事件，测试先核对退款前的控制值，再通过真实 `POST /admin/billing/refund` 退款，查询个人分解、管理概览、年度活动及 PG 日志汇总。查询显式绕过看板缓存。

一次流式 Chat 调用实际得到输入 100、输出 20，共 120 Token，费用 240 micro。退款后 CH 为两条事件、一个 request_id、120 Token、净费用 0。PG 日志汇总为一条记录、已退款一笔；原始财务事实符合预期。

这里的速率只用于同一测试请求退款前后对照，不是供应商或生产性能结论。测量值 66 ms 不被退款改变；已确认的问题包括调用次数、平均 RPM、来源/缓存覆盖分母与输出速度的完整性判定，不能把所有延迟数值一起说成错误。

五次统计 HTTP 请求均为 200。探针在业务数字断言处实际退出 **101：0 passed、1 failed、0 ignored/filtered**，不是编译、授权或依赖失败。失败原文是个人分解 `requests=2`，应为 1。结果 `/tmp/okapi-request-population-v2-report-20261001.json`，完整日志 `/tmp/okapi-request-population-v2-20261001.log`；记录同时保留所有 HTTP 响应、退款前后值与原始控制查询。探针源码 `target/test-evidence/request-population-v2-20261001/source`，生产源码与 v12 一致，仅新增测试文件。最终断言前已删除本探针专用 CH 数据库。

探针的 PG 使用本阶段专用测试数据库，用户与 request_id 均独立；管理概览当日实际只有一个活跃用户、两条请求计数，与该用户原始事件数一致。个人端点以真实认证 key 限定范围。没有运行真实供应商账单或其他业务类型。

## 修复契约

同一个窗口必须明确区分财务事件、已记录的网关调用和测量样本。当前旧 `countState()` 可以证明财务事件数量，不能直接当作调用数。

- 财务聚合保留消费与退款的独立事件和四金额冲销；退款按实际发生日期进入金额统计。Token 是已发生的用量事实，退款不抹掉或复制它。
- 调用计数按终态调用事实计算；当前消费 `log_type=2`、失败 `log_type=5` 属于调用，退款 `log_type=6` 是财务调整。调用与其退款不得形成两次调用；实时多轮、异步任务及兼容日志的计数单位须逐项验证，不直接等同 HTTP 连接数。
- 错误率、平均 RPM、来源占比、缓存/模态/物理单位覆盖率及性能完整性判定使用各自适用的调用与测量样本。退款没有新的上游测量，不作为一个缺失用量或时延的调用样本。
- 财务覆盖检查仍比较全部财务事件；请求测量覆盖检查比较调用事件。不能为修请求数删退款金额，不能将财务覆盖计数与请求计数混用。
- 新的长期聚合保留分类及覆盖来源；完整性不足时先核对可证明完整的 raw。旧聚合丢失了事件类型且 raw 已过期时，不能猜测请求数、把它填零或将退款当作“未知调用”。新旧来源互斥，不能叠加重复覆盖；本地午夜精度沿用 [日历归属契约](billing-calendar-audit.md)。

下一实现先固定跨窗口/原始日志到期后的分类与样本契约，再同步各统计来源、个人/管理读出口、排行与筛选排序。验收至少包括成功、真实失败、同日/跨日退款、反复退款、原始明细保留/到期、半覆盖历史、多时区、字符单位、流式/非流式和缓存明确零/未上报。生产成本覆盖、财务冲销与真实供应商费用语义继续单独核对。

该设计不改变已发布价格、计费公式、钱包流水或投递身份，也不以新的测试定义掩盖旧失败。核心验证目标保持进行中。

## 当前实现与验收进度（2026-10-01）

`ChClient::ensure_schema` 从嵌入式权威 MV 定义生成独立 `population_v1_mv_*` 聚合与 `population_source_v1_mv_*` 读取视图。原表定义不覆盖、不 POPULATE。StateIf 外层筛选经 ClickHouse 24.8 实际执行确认保留原 AggregateFunction 状态类型（count / sum / quantiles / countIf），因此原有 Merge 读取可以继续使用。

新聚合增加 `financial_records`（全部记录）和 `population_classified`（事件类型 2/5/6 的可解释记录）；请求、Token、错误、客户端使用用户及测量状态只采消费/失败，金额、成本覆盖与财务新鲜度采全部财务记录。读取在相同完整维度比较旧记录数与新记录覆盖：完整新源优先，否则选择可证明完整且全部分类的 raw 重算；新旧不相加。旧分类丢失且 raw 不全，调用/测量状态返回 `statistics_request_history_incomplete`，财务专用投影仍可读取旧金额。缓存历史覆盖使用其对应调用母表的记录数，而非仅有上报标记的样本数。

分析明细与旧立方体的补充范围改按财务记录覆盖决定，退款窗口即使调用数为零也不能丢掉负金额；调用测量仍比较调用覆盖。成本覆盖分母是 `financial_records`，新增 `cost_known_records`，原兼容字段 `cost_known_requests` 暂保留相同记录数含义，不能因此把未知供应商费用改成已知。管理日志汇总的金额独立读取完整财务行，RPM/Token/采集样本从调用源读取；原始事件列表保留退款。

固定 v4 底层集成实际 **2 passed、0 failed/ignored/filtered**：一次调用加退款，在 raw 保留与删除后都是 1 调用、2 财务记录、120 Token、净金额 0；旧聚合升级在 raw 完整时重算，raw 删除时拒绝猜调用数但保留财务专用金额。完整日志 `/tmp/okapi-population-v4-integration-20261001.log`。

固定 v5 的实际 HTTP 测试 **0 passed、1 failed、0 ignored/filtered**：退款前统计正确，退款后个人分解返回 500，不能把底层测试当成端点通过。隔离夹具已核对 29 个读取视图财务记录以及 23 个含 requests 的视图调用数（均 1），下一步定位组合查询失败。原始失败保留 `/tmp/okapi-population-v5-http-20261001.log`；后续源码新增错误日志与明确历史错误参数，不降低原来的数字断言。

当前没有变更定价公式或财务事务，没有提交、推送、部署或重启共享服务。跨日、失败、未知事件、部分新聚合与多时区场景继续扩展测试；本轮尚无生产容量或性能结论。

组合查询失败进一步定位为真实 ClickHouse `MEMORY_LIMIT_EXCEEDED`（服务器总内存上限 3.60 GiB），不是请求数或退款金额断言失败。固定 v6 的退款前后个人分解、管理概览已返回正确调用数与覆盖率，年度活动展开恢复视图时触发内存限制；完整失败原文 `/tmp/okapi-population-v6-http-20261001.log`。未提高服务内存或查询护栏。

正在验收的快路径：每次查询先以只包含维度与计数状态的小查询验证各引用 MV 在每个完整粒度的旧记录数、新记录数及分类覆盖；不缓存证明。覆盖完整直接读分类物理聚合，有缺口才展开历史恢复视图。该检查与随后查询是两个 CH 读取，遵循已有异步统计新鲜度边界，不构成跨 MV 的原子财务快照。当前检查覆盖整个引用表，历史基数很大时的成本与有旧缺口的恢复查询资源仍需要性能核对；不能宣传为生产容量验收。
