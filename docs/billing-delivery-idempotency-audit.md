# 统计投递幂等核对

范围：后端 outbox → NATS/直连 → ClickHouse 明细与物化聚合；不改变价格、金额、Token 采集口径或钱包流水。

## 实施协议

- 服务端 outbox 事件 UUID 随 relay 发布，NATS 发布 ID 使用同一身份。
- relay 确认发布标记 stats_protocol=1。回退直连接管新协议已发布但未持久接管的行；NATS 形态超过五分钟未接管时从原 outbox 恢复。原身份使晚到消息无副作用。旧已发布行标记 0，不因缺新回执而盲目重放。
- PG 保存事件回执与不可变批次：最多 500 行，投递前提交原始载荷和冻结 CH 行。并行 worker 以批次锁和 SKIP LOCKED 分工。
- 重试使用原 UUID 批次 token、相同行和相同顺序，新事件单独组批。完成标记与 outbox 标记在同一 PG 事务，失败时保留冻结数据。
- NATS 在 PG 接管事件后 ack；CH 后续重试不依赖消息的消费批次边界。直连和 NATS 共用回执，已完成事件不再次写 CH。
- 失败五次进入 DLQ。选择批次任一 DLQ 成员重投会恢复整个原批次，返回实际恢复的成员数，MCP dry_run 预览 `requeue_members`；普通历史 DLQ 保持原重入 outbox 行为。批次丢弃必须显式选择全部未处理成员，部分选择返回 400/`delivery_batch_members`，无隐式扩大处置；列表可按 batch_id 返回原批次至多 500 个成员并带批次大小。
- 已完成批次清除大载荷但保留身份回执；未完成/DLQ 不清除。未经明确历史重建程序不能删除回执或改变 CH 目标。
- 重投的响应提供实际批次 ID，审计同时保存选择 ID、实际恢复的全部 DLQ ID 和批次 ID；删除 DLQ 后仍可定位操作范围。

健康与分析新鲜度合并尚未分配的 outbox 和已持久接管的 CH 批次，按事件数计算并排除重复计数；NATS 已 ack 不能当作 CH 已完成。原批次丢弃后，已处理的批次 DLQ 不再计为未处理失败；无效消息仍由 DLQ 深度显示。历史无批次 outbox 失败行仍保留原失败状态，旧 DLQ 处置与这些行的关联校准需独立核对，不能把新批次结论套用于历史模糊行。原 outbox 未清理时以原事件创建时间计算排队年龄，清理后使用批次创建时刻作为可证明的下界。

## 未解决边界

后续已对当前计费/统计链路的本地日历归属完成独立固定源码验收，修复非整小时午夜错误与旧日历史被误报为零，见 [Token 与金额的日历归属核对](billing-calendar-audit.md)。该结果与本页投递阶段分别记录，不累计为同一次全工作区验收。

统计事件数与 API 请求数必须分别验收。`mv_user_day.requests` 当前由 `countState()` 保存事件数；同一个 request_id 的消费与退款应保留两个财务事件，不能为降低请求次数而删掉退款。本轮投递去重不证明看板请求次数、延迟或速度的样本范围已正确，相关查询及历史修复仍待独立核对。

CH 去重窗口当前为 1000 个块。CH 成功而 PG 未确认且原 token 已被驱逐时，仅固定批次不能保证永久去重。CH/MV 部分写失败、旧协议模糊批次、老 JS 消息的重复发布、历史修复和大流量性能仍需独立验证。新的身份回执不会自动修正已经重复的历史数据。

升级需先停止旧投递 worker、处理/记录旧协议模糊窗口，再执行迁移和启动新 worker；不能让旧 seq/ID 区间协议与新回执协议混写。为已有 outbox 增加随机 UUID 默认值可能重写大表，维护窗口与数据规模需另行评估。固定 `ingested_at` 记录的是批次准备时刻，事件统计仍按原创建时刻；重试不修改载荷。已完成身份元数据持续增长，保留周期与备份/CH 恢复策略必须覆盖可能的重放范围。
